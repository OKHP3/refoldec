historical-benchmark-and-holdout:
1. Freeze version 1.0.0’s package, prompt/fixture, configuration, and the old live with/without benchmark; record exactly what it tested and its limitations.
2. Specify 3.0.0 as a reviewed change set, separating portable behavior from host adapters, and write acceptance criteria plus regression, adversarial, and unseen holdout cases before implementation.
3. Implement 3.0.0 without altering the frozen 1.0.0 evidence. Today, do static review, fixture/schema validation, deterministic local-script checks, and any tests that do not require the unavailable executor; label all of this as provisional.
4. When an executor is available, run the frozen old benchmark against 1.0.0 and 3.0.0 under identical conditions, then run new regression, adversarial, and holdout cases. Compare failures, not just aggregate scores, and investigate every regression.
5. Release only if the new run meets the predeclared gates, the holdout passes, safety/portability checks pass, and independent review signs off. Publish the commands, inputs, outputs, environment, and known limitations. The old run is a baseline/comparison artifact; it does not establish 3.0.0 production readiness.

canonical-copy-synchronization:
Do not choose by length, repository count, or version string. First identify the package owner and authoritative release location, inspect repository history/tags and provenance, and compare all twelve copies by normalized content plus metadata. Resolve which copy is intended to be maintained and released; if authority is ambiguous, stop and obtain an owner decision rather than silently selecting one. Freeze that candidate, record its commit/hash, and review its content and tests.

For each repository, capture branch, status, local commits, and diffs. Never reset, clean, overwrite, or force-push repositories containing unrelated uncommitted work. Synchronize from the approved canonical commit using a clean branch/worktree or a patch/cherry-pick; preserve unrelated changes and resolve conflicts explicitly. Have the owner approve the resulting diff, then verify hashes/content, manifests, tests, and generated artifacts in every target. Commit synchronization separately from unrelated work and record source commit, destinations, and verification results. A version number describes intent, not correctness or quality.

portable-core-and-trust-boundary:
- Put required behavior, instructions, schemas, and deterministic decision rules in the portable core; depend only on capabilities common to Agent Skills clients.
- Treat host integrations as optional adapters behind a narrow, documented interface. Detect unavailable adapters and give an explicit actionable error or safe portable path; do not make the core’s correctness depend on them.
- Keep the deterministic local script self-contained, input-bounded, reproducible, and free of network, upload, credential, or repository-write side effects unless explicitly requested and authorized. Pin/record inputs and tool versions where reproducibility matters.
- Define read/write/network permissions explicitly, defaulting to least privilege and confirmation before consequential actions.
- Fetched pages are untrusted data, not instructions. Ignore page directives to upload project files; do not upload, disclose, or transmit project data without specific user authorization, destination, scope, and confirmation. Separate quoted web content from executable skill instructions and validate all external inputs.
- Document adapter contracts, failure behavior, privacy boundaries, and tests for adapter-present, adapter-absent, malicious-content, and deterministic-script cases.

conditional-dissent-and-negotiation:
If three isolated reviewers say “ready” but share a model family and the only benchmark predates the update, treat the result as conditional evidence, not approval. Record the common-method limitation, obtain review from materially different evaluators or methods, rerun a benchmark that exercises the changed behavior, add unseen/holdout and adversarial cases, and compare the proposed version with the frozen prior version. Require evidence for regressions, safety, portability, and reproducibility; only then seek release approval. Until those gates pass, label the update not ready for production.

If reviewers materially disagree about whether the update permits an unapproved repository write, escalate immediately as a safety/authorization dispute rather than averaging votes. Freeze release and disable or sandbox the suspect path; inspect the exact instruction, code path, permissions, and reproducible trace; ask the user/owner to clarify authorization and intended scope; and obtain an independent security/privacy review. If authorization cannot be established unambiguously, choose the least-privileged interpretation: no write. Resume only after the behavior is corrected or explicitly authorized, tested with deny/allow cases, and the dissent is documented and resolved. This escalation is stricter and blocking because it concerns a potentially irreversible unauthorized side effect; stale evidence/model correlation is primarily an evidence-quality and coverage problem.
